# GL049 — Deploy job marked interruptible: true

**Severity:** `warn`  
**OWASP:** [CICD-SEC-7 – Insecure System Configuration](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-07-Insecure-System-Configuration)  
**CWE:** [CWE-362 – Concurrent Execution using Shared Resource with Improper Synchronization ('Race Condition')](https://cwe.mitre.org/data/definitions/362.html)

## Risk

When a deployment job is marked `interruptible: true`, GitLab may cancel it mid-execution if a newer pipeline starts (depending on [`workflow:auto_cancel`](https://docs.gitlab.com/ci/yaml/#workflowauto_cancel) settings). A deployment interrupted halfway leaves the target environment in an undefined state: database migrations may be partially applied, containers partially updated, or load-balancer state inconsistent.

`interruptible: true` is appropriate for build, test, and lint jobs — not for jobs that mutate external state.

## What is flagged

Jobs whose name, stage, or [`environment:`](https://docs.gitlab.com/ci/yaml/#environment) key indicates deployment activity and that have `interruptible: true` explicitly set. Matched keywords: `deploy`, `release`, `publish`, `rollout`, `migrat` (migrate, migration), `provision`, `ship`, `push`, `upload`, `dist`. A name or stage whose words say it tests or checks (`test`, `lint`, `check`, `coverage`, `validate`, `audit`, `scan`, `note`, `changelog`, `cleanup`) does not count, and neither does one that builds (`build`, `compile`, `assemble`) unless it also has `deploy`, `publish`, `push`, `upload`, `rollout` or `ship`: `release-build` and `check migrations` are not deployments, `build-and-push` is. An `environment:` with `action: prepare`, `verify` or `access` only uses the environment, and one whose tier is `development` or `testing` (set with `deployment_tier:` or, without one, guessed by GitLab from the name: `review/…`, `qa`, …) is a review or preview target, which a newer pipeline may well cancel; in both cases the name and stage decide.

`interruptible:`, `environment:` and `stage:` count when the job inherits them through `extends:` or `default:`. Hidden jobs (names starting with `.`) are not reported; the jobs extending them are. A job whose only deploy signal is a name keyword and whose stage is a check-only stage (`test`, `lint`, `check`, and the other check words listed above) is not flagged: the stage says the job only tests or checks. A job with a deploy-like stage, or with an `environment:` whose tier is production or staging (set or guessed from the name), is still flagged; an environment of no recognisable tier in a check-only stage is not. The `pages` job (or a job with `pages:`) is not flagged: GitLab Pages publishes only after the job succeeds, so a cancelled run leaves the old site in place.

## Trigger example

```yaml
deploy-production:
  stage: deploy
  interruptible: true
  script:
    - kubectl apply -f k8s/
    - kubectl rollout status deployment/app
```

## Safe alternative

Omit `interruptible` (default is `false`) or set it explicitly, and pair with `resource_group:` to prevent concurrent runs:

```yaml
deploy-production:
  stage: deploy
  interruptible: false
  resource_group: production
  script:
    - kubectl apply -f k8s/
    - kubectl rollout status deployment/app
```

## Notes

- Jobs without an explicit `interruptible: true` are not flagged (default is `false`)
- Non-deployment jobs with `interruptible: true` are not flagged — this is the intended use case
- A name-keyword job in a check-only stage is not flagged (see above)
- See also: GL019 (deploy job without `resource_group:`)
