# GL014 — Environment dumped into an artifact

**Severity:** warn  
**OWASP:** [CICD-SEC-6 – Insufficient Credential Hygiene](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene)

## What glsec checks

glsec flags jobs that combine two things:

1. A script line that writes **all** environment variables to a file: `env`, `printenv`, `export -p` or `cat /proc/self/environ`, redirected with `>` or `>>` or piped into `tee`. The command has to stand at the start of a command, so `printenv HOME > f` (one variable), `env | grep ^APP_ > f` (filtered) and `cat .env > f` don't count.
2. An artifact that uploads it:
   - an `artifacts: reports: dotenv:` entry (any env dump in the job counts), or
   - `artifacts: paths:` that cover the file, or `artifacts: untracked: true`.

Paths are matched as GitLab does: relative to the project directory (`./` and `$CI_PROJECT_DIR/` are stripped), `**` spans directories, `*` and `?` stay within one path segment, a directory or `.` takes everything below it, and `artifacts: exclude:` removes matching files again. A file outside the project directory (`/tmp/env.txt`) is never uploaded through `paths:`; a file named by a variable only counts with `untracked: true`. A job without its own `artifacts:` uses the one in `default:`.

This makes `CI_JOB_TOKEN`, masked CI/CD variables, and any other secrets present in the job environment downloadable by anyone who can read the job's artifacts. Masking only applies to the job log, not to files.

## Trigger examples

```yaml
build:
  script:
    - make build
    - env > build.env          # captures CI_JOB_TOKEN, AWS_SECRET_ACCESS_KEY, etc.
  artifacts:
    reports:
      dotenv: build.env        # downloadable by any pipeline viewer
```

```yaml
diag:
  script:
    - env > diagnostics.txt
  artifacts:
    paths: [diagnostics.txt]   # the whole environment, as a downloadable file
    expire_in: 1 day
```

## Safe alternative

Export only the specific variables that downstream jobs need:

```yaml
build:
  script:
    - make build
    - echo "BUILD_VERSION=$BUILD_VERSION" > build.env
    - echo "IMAGE_TAG=$CI_COMMIT_SHORT_SHA" >> build.env
  artifacts:
    reports:
      dotenv: build.env
```

For diagnostics, write only the variables you need, and never secrets:

```yaml
diag:
  script:
    - echo "CI_COMMIT_SHA=$CI_COMMIT_SHA" > diagnostics.txt
  artifacts:
    paths: [diagnostics.txt]
    expire_in: 1 day
```

## Why this matters

GitLab's `dotenv` report artifact is designed to pass a small set of computed values (e.g. a generated version string) to downstream jobs. When `env >` is used instead, the artifact contains every variable in the job environment, including:

- `CI_JOB_TOKEN` — a scoped GitLab API token
- All CI/CD variables, even those marked as masked (masking only applies to logs, not artifact files)
- Cloud provider credentials, deploy keys, and any other secret injected into the job

Any project member with the Reporter role or above can download pipeline artifacts through the GitLab UI or API.
