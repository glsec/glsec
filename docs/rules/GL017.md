# GL017 — Deploy/publish job has no `tags:` restriction

**Severity:** `warn`  
**OWASP:** [CICD-SEC-5 – Insufficient PBAC](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-05-Insufficient-PBAC)

## What glsec checks

glsec flags deployment and publish jobs that do not restrict which runner can execute them via `tags:`. Without a `tags:` filter, the job runs on any available runner — including compromised or untrusted self-hosted runners that a team may not intend to use for production workloads.

A job is considered a deployment/publish job if it has:

- An `environment:` key, unless its `action:` is `prepare`, `verify` or `access` (those only use the environment), or
- A `stage:` value containing `deploy`, `release`, `publish`, or `ship`

Unlike GL019, review and test environments count, and a `prepare`, `verify` or `access` job in a deploy stage still counts: those jobs get the environment's variables, so the runner they run on matters as much as for a production deploy.

A stage whose words say it tests or checks (`test`, `lint`, `check`, `coverage`, `validate`, `audit`, `scan`, `note`, `changelog`, `cleanup`, matched at the start of a word, so `deployment test` but not `latest`) is not a deploy stage, and neither is a pre-release stage (`prerelease`, `pre-release`, `pre_release`). Nor is one that builds (`build`, `compile`, `assemble`) unless it also names a strong deploy word (`deploy`, `publish`, `push`, `upload`, `rollout`, `ship`): `release-build` builds, `build-and-publish` publishes.

`tags:`, `environment:`, `stage:` and `trigger:` count when the job inherits them through `extends:` (from a job in the same file) or from `default:`, respecting `inherit: default:`. Hidden jobs (names starting with `.`) are templates GitLab never runs, so they are not reported; the jobs extending them are. A job extending a template from another file is skipped. In a file with `include:`, a job without `script:`, `trigger:` or `run:` (its own or from a same-file template) is skipped too: GitLab merges it into the included job of the same name, which may carry the missing key.

## Trigger example

```yaml
deploy-prod:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  # no tags: — runs on any available runner
```

## Safe alternative

```yaml
deploy-prod:
  stage: deploy
  environment: production
  tags:
    - production
    - docker
  script:
    - ./deploy.sh
```

## Why this matters

In organisations that mix GitLab SaaS runners with self-hosted runners, a deploy job without `tags:` may land on a shared or less-trusted runner. If that runner is compromised, secrets injected into the deployment environment (SSH keys, cloud credentials, API tokens) are exposed to the attacker.

Restricting runners with `tags:` ensures only explicitly trusted infrastructure executes sensitive jobs.

## False positives

If you intentionally run all jobs — including deployments — on GitLab SaaS shared runners and have no self-hosted runners in the project, this finding can be suppressed:

```yaml
deploy-prod:
  stage: deploy
  script:
    - ./deploy.sh
  # glsec:ignore GL017 -- SaaS-only project, no self-hosted runners
```
