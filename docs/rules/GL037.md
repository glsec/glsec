# GL037 — `trigger:` job without `inherit: variables: false`

**Severity:** `warn`  
**OWASP:** [CICD-SEC-6 – Insufficient Credential Hygiene](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene)

## What glsec checks

glsec flags `trigger:` jobs that lack `inherit: variables: false` when the pipeline has top-level `variables:` (or `variables:` in a `workflow:rules` entry) with secret-like names (same suffix heuristic as GL006/GL027: `_TOKEN`, `_SECRET`, `_PASSWORD`, `_KEY`, etc.). By default, GitLab forwards all top-level pipeline variables to downstream pipelines — the downstream project receives secrets it was never explicitly granted.

Only variables whose value comes from another variable count, as in `DEPLOY_TOKEN: $PROD_DEPLOY_TOKEN`: that passes a CI/CD setting on. A literal value is in the repository already, and a predefined variable (`$CI_JOB_TOKEN`) is in every pipeline anyway, so forwarding either exposes nothing new. Names ending in a non-secret segment (`_VERSION`, `_URL`, `_NAME`, …) don't count either.

The finding is suppressed when:

- No such top-level variable exists, or
- `inherit: variables: false` is set on the trigger job, or
- `inherit: variables:` is a list that names none of them

A child pipeline (`trigger: include:`) runs in the same project and is not reported; only a multi-project trigger (`trigger: project:`) hands the variables to another project.

## Trigger example

```yaml
variables:
  DEPLOY_TOKEN: $DEPLOY_TOKEN   # top-level — forwarded to all trigger: jobs by default

deploy-to-k8s:
  trigger:
    project: myorg/k8s-deployer
    branch: main
    # inherit: variables: false absent — DEPLOY_TOKEN forwarded implicitly
```

## Safe alternative

```yaml
deploy-to-k8s:
  trigger:
    project: myorg/k8s-deployer
    branch: main
  inherit:
    variables: false   # opt out of implicit forwarding
  variables:
    DEPLOY_ENV: production   # pass only what the downstream actually needs
```
