# GL001 — Mutable image tag

**Severity:** `error` (version-less tags and version tags under the opt-in digest policy: `warn`)  
**OWASP:** [CICD-SEC-3 – Dependency Chain Abuse](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-03-Dependency-Chain-Abuse)  

## Risk

Using `latest`, a branch name, or no tag at all means the image pulled by the runner can change between pipeline runs without any code change. A compromised or hijacked registry tag silently introduces malicious code into your build environment.

## What is flagged

- No tag: `image: alpine` (implicitly pulls `latest`)
- Mutable tags: `latest`, `stable`, `edge`, `dev`, `main`, `master`, `nightly`, `rolling`, `canary`, `beta`, `alpha`, `lts`, `current`, `testing`, `oldstable`
- Version-less tags, as `warn`: any tag with no digit in it, such as `docker:dind`, `docker:dind-rootless`, `node:alpine`, `python:slim`, `gcr.io/kaniko-project/executor:debug` or `debian:bookworm`. These are the `latest` build of a variant or release series, and upstream moves them on every release.
- Applies to `image:` and `services:` at global, `default:`, and job level

SHA256 digest pins (`@sha256:...`) are always safe and never flagged.

## Require image digests (opt-in)

Set `require_image_digest: true` in `.glsec.yml` to also report literal version tags such as `node:22.1.0` and `docker:27.3.1-dind` as `warn`. A version tag can be moved to different content; a [digest identifies fixed image content](https://docs.docker.com/reference/cli/docker/image/pull/#pull-an-image-by-digest-immutable-identifier). Pin with `image@sha256:…` or `image:1.2.3@sha256:…`. This applies to both `image:` and `services:` at global, `default:`, and job level. Known moving tags such as `latest` keep their `error` severity, and the advice under this policy recommends a digest.

The option defaults to `false`, so version tags remain accepted unless enabled. Dynamic references and GitLab-hosted macOS VM image names do not gain digest warnings. Existing checks of values assigned to a bare image variable still apply, as described below. Use `--strict` to make the new warnings fail the scan, or configure GL001's severity explicitly.

## Known attacks

[CVE-2026-33634](https://nvd.nist.gov/vuln/detail/CVE-2026-33634): a malicious Trivy 0.69.4 release reached jobs that pull a moving tag. A version tag is only reported with `require_image_digest: true`, so `aquasec/trivy:0.69.4` itself passes by default.

## Trigger example

```yaml
build:
  image: node:latest        # mutable tag
  script:
    - ./build.sh

test:
  image: alpine             # no tag — defaults to latest
  services:
    - docker:dind           # version-less variant tag (warn)
  script:
    - ./test.sh
```

## Safe alternative

```yaml
build:
  image: node:20.11.0       # pinned version
  script:
    - ./build.sh

test:
  image: alpine@sha256:c5b1261d6d3e43071626931fc004f70149baeba2c8ec672bd4f27761f8e1ad6b
  services:
    - docker:27.3.1-dind    # versioned variant
  script:
    - ./test.sh
```

## Notes

A tag is treated as version-less when it contains no digit. Version-qualified variants (`docker:27-dind`, `python:3.11-slim`, `node:20.11.0-alpine`, `ubuntu:24.04`) pass through. They are reported as `warn` rather than `error`. They float just like `latest`, but a variant tag at least fixes the image flavour, and `docker:dind` in particular appears in a large share of pipelines.

A tag containing a variable (`$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA`, `builder:$TAG-alpine`) is not flagged, since its value is unknown statically. The same goes for a digest from a variable (`${REGISTRY}/kubectl@${KUBECTL_DIGEST}`) and for a reference whose last path segment contains a variable (`${DEPENDENCY_PROXY_PREFIX}${BASE_IMAGE}`, `ci-env$TAG_SUFFIX`): the variable may carry the tag.

An image reference that is a single variable (`image: $MY_IMAGE` or `${MY_IMAGE}`, also in `services:`) is resolved against the values the same file assigns to it, and each value is checked like an inline image:

1. every `parallel:matrix` value of that name in the job, each reported separately;
2. for jobs without such a matrix value, or matrix entries that don't set the name, every value the job's `rules:` entries set, plus the job's own `variables:`;
3. failing that, the top-level `variables:` and every value a `workflow:rules` entry sets, unless `inherit:variables` is `false` or a list that leaves the name out.

The message names both, e.g. `image "$BASE_IMAGE" (= "node:latest") uses mutable tag "latest"`. Top-level variables are not used for hidden jobs (`.template`), whose users may override them, or for jobs that inherit through `extends:`, which glsec does not resolve. YAML merge keys (`<<:`) are resolved. A variable that is not defined in the file, or whose value contains another `$`, is not flagged, since its value is unknown statically. Variables that are never used in `image:` or `services:` (for example a `docker push` target) are not checked. [GL007](GL007.md) still reports the same line, because a pipeline variable can override the value.

The VM images of GitLab-hosted macOS runners (`image: macos-14-xcode-15`) are selected by name, cannot carry a tag, and are not flagged.

Pinning an image prevents tag mutation but does not verify whether the pinned version contains known vulnerabilities. Use a dedicated container scanner such as [trivy](https://github.com/aquasecurity/trivy) as a separate CI job to check for CVEs in pinned images.
