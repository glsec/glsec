# GL027 — Secret-like variable with a value committed in the pipeline file

**Severity:** `warn`  
**OWASP:** [CICD-SEC-6 – Insufficient Credential Hygiene](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene)  
**CWE:** [CWE-798 – Use of Hard-coded Credentials](https://cwe.mitre.org/data/definitions/798.html)

## What glsec checks

glsec flags a variable in long form (a mapping with `value:`, usually with `description:`) whose name ends with a secret-like suffix (`_TOKEN`, `_SECRET`, `_PASSWORD`, `_PASSWD`, `_PASS`, `_PWD`, `_KEY`, `_CREDENTIAL`, `_CERT`) and whose `value:` is a literal. It checks top-level `variables:`, `default:`, jobs, and the `variables:` of `workflow:rules` and job `rules:` entries.

The long form is what pre-fills the **Run pipeline** form. A secret-like value there is in the repository for everyone who can read it, in the form for everyone who can run a pipeline, and in the job log whenever a command prints it. `.gitlab-ci.yml` has no way to mask it: `masked` is not a keyword under `variables:` ([gitlab#424209](https://gitlab.com/gitlab-org/gitlab/-/issues/424209) asks for one). Only CI/CD variables set in the project, group or instance settings can be masked.

**Not flagged:**

- a long-form variable with only `description:`, or an empty `value:`: the person running the pipeline supplies the value
- a `value:` that references another variable (`$PROJECT_DEPLOY_TOKEN`); re-exporting secrets is [GL018](GL018.md)
- obvious placeholders (`changeme`, `example`, `redacted`, `<token>`, `{{ token }}`, `xxx`, `TODO`, ...) and a value that repeats the variable's name (`API_TOKEN: _API_TOKEN_`)
- values in a known token format (`glpat-`, `ghp_`, AWS keys, ...): [GL006](GL006.md) reports those as `error`
- the short form (`POSTGRES_PASSWORD: postgres`). In real pipelines a secret-like name with a literal short-form value is nearly always a throwaway password for a service container or a test mock; real tokens in that form are caught by GL006's formats.

Before 1.23.0 this rule recommended adding `masked: true` to the variable. That keyword doesn't exist, and GitLab's schema rejects it.

## Trigger example

```yaml
variables:
  DEPLOY_PASSWORD:
    value: "staging-pw-2024"
    description: "Password for the staging deploy user"

deploy:
  script:
    - ./deploy.sh
```

## Safe alternative

Store the secret as a masked (and, for deploys, protected) CI/CD variable in **Settings → CI/CD → Variables**. If the pipeline is run by hand and the value should be typed in, keep only the description:

```yaml
variables:
  DEPLOY_PASSWORD:
    description: "Password for the staging deploy user (leave empty to use the masked project variable)"

deploy:
  script:
    - ./deploy.sh
```
