# GL062 — `printenv`, `env`, `set` and other full dumps leak every variable to the job log

**Severity:** `warn`  
**OWASP:** [CICD-SEC-6 – Insufficient Credential Hygiene](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene)  
**CWE:** [CWE-532 – Insertion of Sensitive Information into Log File](https://cwe.mitre.org/data/definitions/532.html)

## Risk

Running a command that prints the whole environment in a CI script dumps every environment variable to the job log — including all CI/CD secrets, tokens, and masked variables. GitLab masks known secret variable values in logs, but masking is not guaranteed for all formats (short values, values with special characters, values that appear mid-line). Any third party with read access to the job log can potentially extract credentials.

The rule covers every common spelling of that dump: `printenv`, bare `env` (also `env -0`/`env --null`), bare `set`, `export` and `export -p`, `declare`/`typeset` bare or with only `-p`/`-x`, `cat /proc/self/environ`, and the PowerShell `env:` drive (`gci env:`, `Get-ChildItem env:`, `dir env:`, `ls env:`, `Get-Item env:*`).

[GL021](GL021.md) already flags `echo`/`printf` of individual secret variables. This rule covers the broader pattern of dumping the entire environment.

## Trigger example

```yaml
debug:
  script:
    - printenv   # dumps all variables to the log
    - env
    - set
    - export -p
    - declare -p
    - env -0
    - cat /proc/self/environ
```

```yaml
win-debug:
  tags: [windows]
  script:
    - 'gci env:'
    - 'Get-ChildItem env: | Format-Table'
```

`/usr/bin/env`, and forms with shell separators (`printenv && ...`, `cd /tmp; env`), are also detected.

## What is not flagged

- Output captured by a command substitution: `X=$(env | grep …)`, `for v in $(env | …)`, `unset $(env | …)`. It goes to a variable or an argument, not to the log.
- `env | grep THREADS` — a filter to one literal variable name without a secret-like word (and not a `CI` or `GITLAB` prefix), like `printenv THREADS`. A broader filter is reported with a message naming the pattern.
- Output redirected to a file: `env > env.txt`, `set > vars.txt` (writing it into an uploaded artifact is [GL014](GL014.md)).
- `printenv VAR_NAME`, `declare -p VAR_NAME`, `typeset -x VAR_NAME` — printing a specific variable (same risk class as `echo`, covered by GL021)
- `env VAR=value command` — setting a variable for a subprocess
- `env python script.py` — using `env` as a command runner
- Shell options that change behaviour instead of printing: `set -e`, `set -u`, `set -euo pipefail`, `set -o pipefail`, `set +x`, `set --`
- Assignments and attribute changes: `export FOO=bar`, `export PATH="$PATH:/x"`, `declare -r foo=bar`, `declare -a arr=(1 2)`, `declare -x FOO=bar`
- PowerShell single-variable reads: `$env:PATH`, `Get-ChildItem env:PATH`, `Get-Item env:FOO`. The `env:` drive only counts when it is the whole path argument (`env:` or `env:*`).
- Quoted text that only mentions a newly supported command: `echo "hello; set; done"`, `echo 'declare -p'`. Legacy `env`/`printenv` matching is preserved, including commands inside `sh -c` payloads.

## Safe alternative

Print only the specific variables needed for debugging:

```yaml
debug:
  script:
    - echo "CI_COMMIT_REF=$CI_COMMIT_REF_NAME"
    - echo "DEPLOY_ENV=$DEPLOY_ENV"
```

## Notes

- Severity is `warn`.
- Existing `env`/`printenv` messages are unchanged; findings for the additional dump forms name the command.
- PowerShell filtering pipelines and `Out-File` handling are tracked in [#1172](https://github.com/glsec/glsec/issues/1172); a filtered `env:` listing can still be reported.
- Related: [GL014](GL014.md) (the same dump written into an uploaded artifact), [GL021](GL021.md) (individual secret printed via echo/printf), [GL033](GL033.md) (`CI_DEBUG_TRACE` exposes all variables).
- Script-line rule; the shell forms follow POSIX shell, and the PowerShell `env:` drive is recognised for Windows runners (see [Shell assumptions](../usage.md#shell-assumptions)).
- Suppress per-file with `.glsec-ignore` or inline `# glsec:ignore GL062`.
