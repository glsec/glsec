# GL013 — Production deploy or Pages job without branch restriction

**Severity:** warn  
**OWASP:** [CICD-SEC-1 – Insufficient Flow Control Mechanisms](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-01-Insufficient-Flow-Control-Mechanisms)

## What glsec checks

glsec flags jobs that deploy to a production-like environment but have no `rules:` or `only:` clause to restrict which branches or conditions can trigger the deployment, or one that lets them run only in merge request pipelines, or a `rules:` entry that lets any branch run a production deploy (see below).

A job is considered production-like if either:

- its `environment:` name has a whole component (case-insensitive) `production`, `prod`, `live`, or `staging`, separated by non-alphanumeric characters; `preprod` and `pre-production` count, but `nonprod` and `non-prod` do not; or
- its [`environment:deployment_tier`](https://docs.gitlab.com/ci/yaml/#environmentdeployment_tier) is `production` or `staging` — this catches jobs whose name is an arbitrary string (e.g. `my-app`, `eu-west`) but which declare themselves a prod/staging target via the structured field.

Both the scalar form and the `{name: ..., url: ...}` mapping form are checked.

A [GitLab Pages](https://docs.gitlab.com/user/project/pages/) job counts as a production deploy too: a job named `pages`, or any job with a [`pages:`](https://docs.gitlab.com/ci/yaml/#pages) key, unless `pages: false` or it sets `pages:path_prefix` (a parallel deployment next to the main site). The most recent Pages job replaces the main site whatever branch it ran on, so an unrestricted one lets anyone who can push a branch change the public site, for example documentation with install instructions, without a review.

`rules:`, `only:`, `environment:` and `pages:` count when the job inherits them through `extends:` from a job in the same file or a resolved local `include:`. Hidden jobs (names starting with `.`) are templates GitLab never runs, so they are not reported themselves, and a job that extends an unresolvable cross-file template (such as a remote `include:` or a scan without include resolution) is skipped because the guard may be there. In a file with `include:`, a job without `script:`, `trigger:` or `run:` (its own or from a same-file or resolved local-include template) is skipped too: GitLab merges it into the included job of the same name, which may carry the missing key.

### Deploys that run only in merge request pipelines

A `rules:` or `only:` clause doesn't restrict the job when it lets the job run only in merge request pipelines. Such a pipeline builds the MR's source commit before anyone has reviewed or merged it. A production deploy job is reported when every rule that lets it run (`when: never` rules aside) requires a merge request pipeline:

- `$CI_PIPELINE_SOURCE == "merge_request_event"`, also `=~ /merge_request/`, or
- a positive test of a `$CI_MERGE_REQUEST_*` variable: `$CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"`, `$CI_MERGE_REQUEST_TARGET_BRANCH_PROTECTED == "true"`, `$CI_MERGE_REQUEST_SOURCE_BRANCH_PROTECTED == "true"`, `$CI_MERGE_REQUEST_LABELS =~ /deploy/`, `$CI_MERGE_REQUEST_APPROVED == "true"`, or `$CI_MERGE_REQUEST_IID` alone.

The legacy `only: [merge_requests]` is reported the same way.

None of these is a branch restriction. The MR author picks the target branch, and `TARGET_BRANCH_PROTECTED` is true as soon as the MR targets a protected branch. In a fork MR, `SOURCE_BRANCH_PROTECTED` is decided by the fork's own settings. A rule that also tests `$CI_COMMIT_BRANCH` or `$CI_COMMIT_TAG` belongs to a branch or tag pipeline and isn't counted. Neither is an `environment:action` of `prepare`, `verify`, `access` or `stop`. Only production counts here: a name with a `production`, `prod` or `live` component (excluding pre-production and staging), or `deployment_tier: production`. Staging and review apps often get one environment per MR, so deploying MR code to them is intended and not reported.

```yaml
deploy-prod:
  environment: production
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"
  script: ./deploy-to-prod.sh
```

Protected environments with required approvals, and protected variables (which a pipeline for an unprotected source branch doesn't receive), can lower the risk. They are not visible in the pipeline file, so they don't silence the finding.

### Rules entries that match on any branch

GitLab runs a job by the first `rules:` entry that matches, so one entry that matches on any branch is enough to deploy from it, whatever the other entries restrict (#1486). A production deploy job (the same production names and tier as above, staging left out) is reported at the first entry that can run it and:

- has no `if:` — only `changes:` or `exists:` (also true for new branches and for pipelines without a push event), or `when:` alone, such as a `- when: manual` fallback after a default-branch rule;
- has an `if:` that only tests that a branch is set: `$CI_COMMIT_BRANCH`, `$CI_COMMIT_REF_NAME`, also with `!= null`; or
- has an `if:` that admits `merge_request_event`, unless the condition restricts to a protected ref in every alternative. This needs merge request pipelines to run, so a `workflow:rules` without them silences it.

```yaml
deploy-prod:
  environment: production
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - when: manual          # any branch can deploy by hand
  script: ./deploy-to-prod.sh
```

An earlier `when: never` entry that keeps unprotected refs out restricts every entry after it: `$CI_COMMIT_REF_PROTECTED != "true"` (or `== "false"`), `$CI_COMMIT_BRANCH != $CI_DEFAULT_BRANCH` or `!= "main"`, `$CI_COMMIT_TAG == null`, or `$CI_COMMIT_BRANCH`/`$CI_COMMIT_TAG !~ /pattern/`, also as one `||` alternative. An unconditional `- when: never` ends the rules. Not reported: an entry whose `if:` tests something else, such as a pipeline source (`schedule`, `trigger`, `web`) or a project's own variable (`$PIPELINE_TYPE == "release"`), since whether an unprotected branch can reach it depends on project settings the file doesn't show; rules with a `!reference` glsec can't resolve; and `only:`/`except:`.

A top-level `workflow:rules` that only admits protected refs (the default branch, tags, `$CI_COMMIT_REF_PROTECTED == "true"` or a named branch, and no merge request pipelines) keeps every branch out, so no finding is reported then. So does a `when: never` entry that comes before every other entry and is true on every unprotected ref, such as `- if: $CI_COMMIT_REF_PROTECTED != "true"` with `when: never`.

The same holds for a child pipeline whose every trigger job runs on protected refs only, and for a file included only through `include:` entries whose `rules:` admit protected refs only (#1502). In a child pipeline that a trigger job starts on any ref, an entry `if: $CI_PIPELINE_SOURCE == "parent_pipeline"` is true on every branch and is reported like any other open entry.

## Trigger example

```yaml
deploy-prod:
  stage: deploy
  environment: production   # no rules: — any branch can deploy
  script: ./deploy-to-prod.sh

deploy-eu:
  stage: deploy
  environment:
    name: eu-west           # name not a prod keyword …
    deployment_tier: production   # … but the tier declares it production
  script: ./deploy-to-prod.sh

pages:                      # publishes the main Pages site from any branch
  script: mkdocs build -d public
  artifacts:
    paths: [public]

deploy-from-mr:
  stage: deploy
  environment: production
  rules:                    # only in MR pipelines — deploys unmerged code
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script: ./deploy-to-prod.sh
```

## Safe alternative

Restrict the job to the default protected branch:

```yaml
deploy-prod:
  stage: deploy
  environment: production
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH && $CI_COMMIT_REF_PROTECTED == "true"'
  script: ./deploy-to-prod.sh
```

The same guard works for Pages, as in GitLab's own Pages templates:

```yaml
pages:
  script: mkdocs build -d public
  artifacts:
    paths: [public]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

Or with the legacy `only:` syntax:

```yaml
deploy-prod:
  stage: deploy
  environment: production
  only:
    - main
  script: ./deploy-to-prod.sh
```

## Why this matters

Without a branch restriction:

- Any developer with pipeline trigger access can deploy to production from any branch
- Hotfix or feature branches can accidentally deploy untested code
- Manual pipeline runs from the GitLab UI can bypass normal review workflows
- GitLab's environment protection rules (defined in Settings → CI/CD → Environments) are a second line of defence, not a substitute for restricting which pipelines can target the environment
