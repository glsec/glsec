# GL005 — Sensitive artifacts

**Severity:** `error` (sensitive paths, broad uploads, `.git`, absolute paths, path traversal) / `warn` (missing `expire_in`)  
**OWASP:** [CICD-SEC-6 – Insufficient Credential Hygiene](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene)  
**CWE:** [CWE-23 – Relative Path Traversal](https://cwe.mitre.org/data/definitions/23.html)

## Risk

Storing secrets in job artifacts exposes them to anyone with read access to the project and its pipelines. Absolute paths and path traversal sequences can exfiltrate arbitrary host files on shell-executor runners. Without `expire_in`, artifacts are kept as long as the instance default allows (30 days on GitLab.com; a self-managed instance may keep them forever), compounding the exposure window.

## What is flagged

Applies to `artifacts:` at `default:` and job level, including hidden templates. Sensitive filenames, whole-directory paths and `.git` are checked only under `paths:`; absolute paths and `../` are checked under both `paths:` and `exclude:`.

**Broad uploads (`error`):**

Paths `.`, `./`, `*`, `**`, `$CI_PROJECT_DIR` and `${CI_PROJECT_DIR}` upload the whole working directory, potentially including credentials the job generated, such as `.npmrc`, kubeconfig or `.env`. A trailing `/` is also recognised. A path with a complete `.git` segment, such as `.git/` or `foo/.git/**`, can expose repository history and Git configuration; Git LFS's log directory (`.git/lfs/logs/`) holds neither and is not flagged. `.github/`, `.gitlab/` and `.gitignore` do not match.

Paths are checked where written, with one finding per offending path.

**GitLab Pages (`error`, #1499):**

A Pages job is a job named `pages` or one with a `pages:` key other than `false`. Its publish directory goes into the artifacts (since GitLab 17.10, [`pages.publish`](https://docs.gitlab.com/ci/yaml/#pagespublish) is appended to `artifacts:paths`), and GitLab Pages serves every file in it as the website, dotfiles and `.git/` included. On GitLab.com, a site published that way returned `.git/HEAD`, `.git/config` and `.git/index`. The served `.git/config` held the runner's clone URL with the job token in it. That token expires when the job ends.

Two cases are reported:

- **A publish directory that is the whole working directory or holds `.git`.** This covers `pages: publish: .`, `./` or `$CI_PROJECT_DIR`, and the deprecated top-level `publish:`. If an `artifacts:paths` entry of the same job already uploads `.`, only that entry is reported.
- **A script that copies the project directory into the publish directory without excluding `.git`.** The publish directory is `public` unless `publish:` names another one. Examples are `rsync -a --exclude=public ./ public/` and `cp -r . public/ || true`. Not reported:
  - an rsync `--exclude` whose pattern matches `.git` (`.git`, `.git/`, `.*`, `*`), `-C`, or a filter file;
  - a later `rm -rf public/.git`;
  - a `cp` without `||` after it, because copying a directory into itself fails and the job then deploys nothing;
  - `cp -r * public`, GitLab's plain-HTML pattern, because `*` doesn't match dotfiles.

```yaml
pages:
  script:
    - mkdir -p public
    - rsync -av --exclude=public ./ public/   # copies .git too: add --exclude=.git
  pages:
    publish: public
```

**Absolute paths (`error`):**

A path starting with `/` references the host filesystem directly. On a shell executor this can exfiltrate any file the runner user can read.

**Path traversal (`error`):**

A path containing `../` attempts to escape the project directory.

**Sensitive file patterns (`error`):**

| Pattern | Examples |
|---------|---------|
| `.env`, `.env.*` | `.env`, `.env.production` |
| `*.pem`, `*.der` | `cert.pem`, `ca.der` |
| `*.key` | `server.key`, `private.key` |
| `*.p12`, `*.pfx`, `*.jks`, `*.keystore` | Certificate keystores |
| `id_rsa`, `id_ecdsa`, `id_ed25519`, `id_dsa` | SSH private keys |
| `kubeconfig`, `*.kubeconfig` | Kubernetes config files |
| `*secret*`, `*.secret` | Secret file names |
| `*credential*`, `*credentials*` | Credential file names |
| `*password*`, `*passwd*` | Password file names |
| `*.token` | Token files |
| `*.tfstate`, `*.tfstate.backup`, `*.tfvars` | Terraform state, its backup and variable files |
| `.npmrc`, `.yarnrc.yml` | npm and Yarn auth tokens |
| `.pypirc` | PyPI upload token |
| `.netrc`, `_netrc` | Login credentials for curl, git and other tools |
| `.docker/config.json`, `.dockercfg` | Registry auth after `docker login` |

`.docker/config.json` is matched with its `.docker/` directory, at any depth (`.docker/config.json`, `home/.docker/config.json`); a bare `config.json` is usually an app config and is not flagged.

`.npmrc` and `.yarnrc.yml` are not flagged when every job that uploads them writes the file in its script with a placeholder that npm or Yarn resolves when it reads the file, so the artifact holds the placeholder and no token (#1171):

```yaml
publish:
  script:
    - echo "${NPM_PROJECT_LEVEL_ENDPOINT}:_authToken=\${CI_JOB_TOKEN}" >> .npmrc   # \$ — not expanded
    - npm publish
  artifacts:
    paths: [.npmrc]
    expire_in: 1 day
```

Every write must be `echo`, `printf` or `cat` of a here-document (also through `tee` or in a `{ …; }` or `( … )` group), and none may expand a secret-like variable (`"…=${NPM_TOKEN}"`, unquoted `$NPM_TOKEN`, an unquoted here-document, or a command substitution). In the value of a credential key (`_authToken=`, `_auth=`, `_password=` in `.npmrc`, `npmAuthToken:` and `npmAuthIdent:` in `.yarnrc.yml`) any expanded variable counts, whatever its name, so `_authToken=$TOKEN` is flagged; `${NPM_PROJECT_LEVEL_ENDPOINT}` before the key is not a value. A file test (`[[ -f .npmrc ]]`, `test -f`) or `touch` before the write is fine. The file stays flagged when the job doesn't write it, also writes it another way (`envsubst`, `cp`, `sed -i`, `npm config set`, `npm login`, `yarn npm login`), changes directory, or when the `artifacts:` block is under `default:`. `.netrc`, `.pypirc` and `.docker/config.json` are read literally and are always flagged.

**Unredacted secret scanner report (`error`):**

A gitleaks report holds every secret the scan found, in plain text, unless gitleaks runs with `--redact`. An `artifacts:paths` entry that uploads a report the job's own script writes (`gitleaks … --report-path <file>` or `-r <file>`, through `detect`, `git` or `dir`) is flagged, whether the entry names the file, a directory that holds it, or a glob that matches it:

```yaml
secret-scan:
  script:
    - gitleaks detect --source . --report-path gitleaks-report.json
  artifacts:
    when: always
    paths: [gitleaks-report.json]   # every finding, secret included
    expire_in: 1 week
```

Not flagged: a report written with `--redact` or `--redact=<percent>` other than `0` (`--redact=0` redacts nothing), a report that isn't uploaded, and a gitleaks command that only appears in `echo` text. The job's script includes what it inherits through `extends:`. GitLab's own Secret Detection report is not affected: its analyzer masks the values. A job that runs gitleaks itself and names its report `gl-secret-detection-report.json`, for example one that overrides the template's `secret_detection` job, is flagged like any other.

**Saved Terraform plan (`error`):**

`terraform plan -out=<file>` saves a binary plan that holds the full configuration, a state snapshot and the variables in plain text, including the sensitive values the printed plan shows as `(sensitive value)`. An `artifacts:paths` entry that uploads a plan the job's own script saves is flagged, whatever `-out` names the file (`tfplan`, `planfile`, `plan.out`, `$ENV.plan`):

```yaml
plan:
  script:
    - cd terraform
    - terraform plan -out=tfplan
  artifacts:
    paths: [terraform/tfplan]   # readable by everyone who can see the pipeline
    expire_in: 1 day
```

Terraform, OpenTofu (`tofu`) and Terragrunt (also `run-all plan`) are recognised, with `-out=<file>`, `-out <file>` and `--out`. Because the job usually plans in a subdirectory (`cd`, `-chdir`) that `-out` doesn't name, an entry matches when its file name equals the plan's (`terraform/tfplan`, `${TF_ROOT}/tfplan`) or its glob matches it (`*.tfplan`), or when it is a directory that holds the plan's path as written. `$VAR` and `${VAR}` compare equal.

Not flagged: a job whose `artifacts:access` is `developer`, `maintainer` or `none`, or that sets `public: false` (also through `extends:`), since then anonymous users, Guests and Reporters can't download the plan from the UI or API (job tokens still can, see [GL073](GL073.md)); an uploaded text rendering (`terraform show tfplan > tfplan.txt`), an encrypted copy (`tfplan.enc`), and a plan kept in `cache:` instead of `artifacts:`. A plan saved with GitLab's `gitlab-terraform` wrapper (`plan.cache`) or that an `artifacts:paths` entry in a hidden template uploads for the jobs extending it, is not detected. The job's script includes what it inherits through `extends:`.

To keep the plan for a later apply job, set `artifacts:access: developer` and keep `expire_in` short.

**Missing `expire_in` (`warn`):**

Any `artifacts:` block without an `expire_in` key. Artifacts kept for the instance default, possibly forever, increase the blast radius of any sensitive content they contain.

`expire_in` is checked on the jobs GitLab runs. `artifacts:` is deep-merged along `extends:`, so an `expire_in` in a template the job extends counts, and a template's `artifacts:` without one is reported at the template, once for the jobs that use it. Hidden jobs (names starting with `.`) are not checked for `expire_in` themselves; their paths are. A job extending a template from another file is skipped. In a file with `include:`, a job without `script:`, `trigger:` or `run:` (its own or from a same-file template) is skipped too: GitLab merges it into the included job of the same name, which may carry the missing key.

## Trigger examples

```yaml
build:
  artifacts:
    paths:
      - /etc/passwd                   # absolute path — host filesystem
      - ../../etc/shadow              # path traversal — escapes project dir
      - .env                          # sensitive file pattern
      - deploy.pem                    # private key
    # no expire_in — artifacts kept forever
  script:
    - ./build.sh
```

Whole-directory uploads and `.git` paths are also flagged, even with an expiry:

```yaml
build:
  script: make
  artifacts:
    paths:
      - ./
      - .git/
    expire_in: 1 day
```

## Safe alternative

```yaml
build:
  artifacts:
    paths:
      - dist/
      - build/
    expire_in: 1 week
  script:
    - ./build.sh
```

Never include secret files in artifact paths. Use [GitLab CI/CD variables](https://docs.gitlab.com/ci/variables/) with the Masked flag for secrets.

## Notes

- Absolute path and path traversal checks are active vulnerability indicators on shell-executor runners; on Docker executors the Runner enforces project-directory boundaries at upload time, making these defence-in-depth catches
- Pattern matching for sensitive filenames is case-insensitive and uses glob-style prefix/suffix matching
- GitLab's own Secret Detection artifacts — `gl-secret-detection-report.json` and the `secret-detection-rules.zip` ruleset bundle — are findings reports about secrets, not secret-bearing files, and are not flagged even though their names match `*secret*`
- `expire_in` is flagged as a separate finding regardless of whether other issues are present
