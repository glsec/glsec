# GL046 — Cache poisoning across the protected-branch boundary

**Severity:** `warn`; `error` for `cache: unprotect: true` on deploy-like or merge request jobs  
**OWASP:** [CICD-SEC-3 – Dependency Chain Abuse](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-03-Dependency-Chain-Abuse)  
**CWE:** [CWE-494 – Download of Code Without Integrity Check](https://cwe.mitre.org/data/definitions/494.html)

## Risk

By default GitLab keeps the caches of protected and unprotected refs in separate namespaces, so a pipeline on an unprotected branch cannot write a cache slot that a protected or release pipeline restores. [`cache: unprotect: true`](https://docs.gitlab.com/ci/yaml/#cacheunprotect) removes that separation — in GitLab's words, "users without access to protected branches can read and write to cache keys used by protected branches". Anyone who can push a branch can then pre-fill the cache with malicious build artefacts (e.g. tampered `node_modules/`, compiled binaries), and a later legitimate build restores and executes them without integrity verification.

## What is flagged

The cross-trust-boundary risk requires `cache: unprotect: true`; without it, the namespace separation holds and a per-branch cache key is not a cross-boundary concern. GL046 therefore flags `unprotect: true` caches that can be written, and, under `unprotect: true`, a cache **key** steered by a user-controlled variable.

### `cache: unprotect: true` on a job that writes the cache

An entry is flagged when it sets `unprotect: true` and can write the cache: `policy: pull-push` (the default), `policy: push`, or a policy taken from a variable, which cannot be resolved statically. `policy: pull` only reads and is not flagged. Severity is `error` for deploy-like jobs (name, stage, or `environment:`) and for jobs that run on merge request pipelines, `warn` otherwise, including under `default:`.

```yaml
build:
  cache:
    key: deps
    unprotect: true      # shared with unprotected branches, written by this job
    paths:
      - vendor/
```

Not flagged:

- Jobs that run only on the default branch or on protected refs — every `rules:` entry that can run the job requires `$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH`, `$CI_COMMIT_BRANCH == "main"`/`"master"`, or `$CI_COMMIT_REF_PROTECTED == "true"` (or `only:` lists nothing but `main`/`master`). Writing the shared cache from the protected side is the documented use of `unprotect:`. A **steerable key** on such a job is still flagged (next section), because an unprotected pipeline can pre-fill the slot it restores.
- Hidden template jobs (`.name`). The job that extends them decides where they run, and that job is checked with the template's `cache:` merged in.

Caches defined behind a YAML anchor (`cache: *deps` or `<<: *deps`) are checked like inline ones. A cache used by several jobs is reported once, at its definition, with the highest severity any of those jobs gives it.

### Cache key from a user-controlled variable, under `unprotect: true`

Once a cache sets `unprotect: true`, a `key:` (or `key: prefix:`) steered by a user-controlled predefined variable lets an attacker aim which slot they poison. This matters for a protected-ref-only job that restores such a cache: its own `unprotect: true` is otherwise the documented pattern (above), but a steerable key still lets an unprotected pipeline pre-fill the slot it reads. A steerable key **without** `unprotect: true` is not flagged — the separate namespaces mean a branch name can't steer what a protected pipeline restores.

**Steerable key variables:**

| Variable | Controlled by |
|----------|--------------|
| `$CI_COMMIT_REF_NAME` | Pusher (branch or tag name) |
| `$CI_COMMIT_REF_SLUG` | Pusher (normalised branch/tag name) |
| `$CI_COMMIT_BRANCH` | Pusher (branch name) |
| `$CI_COMMIT_TAG` | Pusher (tag name) |
| `$CI_COMMIT_TITLE` / `$CI_COMMIT_MESSAGE` | Commit author |
| `$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME` | MR author |
| `$CI_MERGE_REQUEST_TITLE` | MR author |
| `$CI_PIPELINE_NAME` | API caller |
| `$CI_EXTERNAL_PULL_REQUEST_SOURCE_BRANCH_NAME` | External pull request author |
| `$CI_CONFIG_REF_URI` | Pusher (ends in the branch name) |
| `$CI_RELEASE_DESCRIPTION` | Release author |
| `$AI_FLOW_INPUT` / `$AI_FLOW_CONTEXT` | Author of the comment or merge request that triggered a GitLab Duo flow |

Fix: drop `unprotect:`, or set `policy: pull` on jobs that share the cache with unprotected branches and build it only on protected ones.

## Trigger examples

```yaml
build:
  cache:
    key: deps
    unprotect: true                 # merges protected and unprotected caches
    paths:
      - node_modules/
  script:
    - ./build.sh

warm-cache:
  rules:
    - if: $CI_COMMIT_REF_PROTECTED == "true"   # protected-only, but…
  cache:
    key: $CI_COMMIT_REF_SLUG        # …a steerable key under unprotect: true
    unprotect: true
    paths:
      - node_modules/
  script:
    - ./build.sh
```

## Safe alternative

Key the cache on a file hash instead of a branch name. This makes the key deterministic and independent of attacker-controlled input:

```yaml
build:
  cache:
    key:
      files:
        - package-lock.json   # cache invalidates when lockfile changes
    paths:
      - node_modules/
  script:
    - ./build.sh
```

## Notes

- Per-branch caches keyed on `$CI_COMMIT_REF_NAME`/`$CI_COMMIT_REF_SLUG` are a common and documented GitLab CI pattern and are **not** flagged on their own: GitLab keeps protected and unprotected caches in separate namespaces, so a branch name can't steer what a protected pipeline restores. The cross-boundary risk only appears with `cache: unprotect: true`, which is what this rule keys on (#1105).
- A static key or a key based only on internal variables (e.g. `$CI_PROJECT_ID`) is safe.
