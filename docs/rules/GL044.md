# GL044 — Untrusted MR source checkout in pipeline context

**Severity:** `warn`  
**OWASP:** [CICD-SEC-4 – Poisoned Pipeline Execution](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-04-Poisoned-Pipeline-Execution)  
**CWE:** [CWE-829 – Inclusion of Functionality from Untrusted Control Sphere](https://cwe.mitre.org/data/definitions/829.html)

## Risk

GitLab CI pipelines triggered by merge requests run on the source branch — code controlled by the MR author. If a job in such a pipeline checks out the merge request source branch — by its commit SHA (`$CI_MERGE_REQUEST_SOURCE_BRANCH_SHA`) or by its branch name (`$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`, which resolves to the live branch tip) — and then executes code from that checkout, it runs **attacker-controlled code** with access to `$CI_JOB_TOKEN` and any protected variables available to the job. The branch-name form is if anything worse: it fetches whatever is at the tip at run time, not even the commit that was reviewed.

This is a Poisoned Pipeline Execution (PPE) attack: the attacker opens an MR with malicious script content, which the pipeline then executes in a trusted context.

## What is flagged

Jobs that combine:

1. A trigger on merge request events (`rules:if` containing `merge_request_event` or `merge_requests`, or the legacy `only: [merge_requests]`)
2. Any of:
   - `script:` or `before_script:` checking out the source branch (`git checkout`, `switch`, `reset`, `restore` or `worktree`) by its SHA (`$CI_MERGE_REQUEST_SOURCE_BRANCH_SHA`) or its name (`$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`, including `origin/$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`), or `git checkout FETCH_HEAD` after fetching either. Both POSIX shell form (`$VAR`, `${VAR}`) and PowerShell form (`$env:VAR`, `${env:VAR}`) are recognised.
   - `image:` referencing `$CI_MERGE_REQUEST_SOURCE_BRANCH_SHA` (attacker-controlled container image)

Reading history (`git log`, `git rev-list`, `git diff`, `git fetch` alone, `commitlint --to`) checks nothing out and is not reported: a merge request pipeline runs the source branch's code anyway, and the variable adds nothing to it.

## What is not flagged

- **Same-project merge requests.** A job whose `rules:` confine it to merge requests from a branch in the same project (an allow rule comparing `$CI_MERGE_REQUEST_SOURCE_PROJECT_PATH`/`_ID` equal to `$CI_MERGE_REQUEST_PROJECT_PATH` or `$CI_PROJECT_ID`) never runs for a fork, so the MR author is already a project member and the source is not attacker-controlled. A `when: never` rule carrying that comparison is the opposite (it excludes same-project MRs and leaves forks) and does **not** suppress the finding.
- **The target branch.** `$CI_MERGE_REQUEST_TARGET_BRANCH_NAME` is not attacker-controlled; checking it out, including `FETCH_HEAD` after fetching the target, is not reported.

## Trigger example

```yaml
security-scan:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - git checkout $CI_MERGE_REQUEST_SOURCE_BRANCH_SHA
    - ./scan.sh   # executes attacker-controlled code with $CI_JOB_TOKEN access
```

The branch-name form, fetching the live tip and running it, is flagged the same way:

```yaml
perf-benchmark:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - git fetch origin "$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME"
    - git checkout -f FETCH_HEAD
    - make bench   # runs attacker-controlled code with $CI_JOB_TOKEN access
```

A Windows job using PowerShell syntax is flagged the same way:

```yaml
test:
  tags: [windows]
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - git fetch origin $env:CI_MERGE_REQUEST_SOURCE_BRANCH_SHA
    - git checkout $env:CI_MERGE_REQUEST_SOURCE_BRANCH_SHA
```

## Safe alternatives

**Run MR pipelines without access to protected variables:**

Use `inherit: variables: false` combined with an explicit allowlist of non-sensitive variables, or run the job in a dedicated MR-only project with no protected variables.

**Use GitLab's built-in MR diff analysis instead of checkout:**

For code analysis, use GitLab's native SAST/code quality runners or CI components that analyse the MR diff without executing code from the source branch.

**Only run trusted code in protected contexts:**

Structure your pipeline so that jobs with access to `$CI_JOB_TOKEN` or protected variables only run on protected branches, never on MR source branches:

```yaml
deploy:
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH   # protected branch only
  script:
    - ./deploy.sh
```

## Notes

- The source-branch variables are only flagged when they drive a **checkout** (`git checkout`/`switch`/`reset`/`restore`/`worktree`, or `FETCH_HEAD` after fetching them). Referencing `$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME` for logging, artifact naming or a commit message is not flagged
- PowerShell variable names are case insensitive, so `$env:ci_merge_request_source_branch_sha` is flagged too; POSIX shell variables are case sensitive, so a lowercase `$ci_merge_request_source_branch_sha` in a POSIX command is a different variable and is not flagged
- The risk exists regardless of whether explicit secrets are referenced; `$CI_JOB_TOKEN` is always available and grants read access to the GitLab API on behalf of the pipeline
