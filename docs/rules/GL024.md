# GL024 — Shell pipe without `set -o pipefail`

**Severity:** `warn`  
**OWASP:** [CICD-SEC-7 – Insecure System Configuration](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-07-Insecure-System-Configuration)

## What glsec checks

glsec flags jobs that use shell pipes (`|`) in their scripts without enabling `pipefail`. By default, a pipeline's exit code is the exit code of the **last** command in the chain. If any earlier command fails, the failure is silently discarded and the job continues.

Pipelines whose commands before the last are simple `echo` or `printf` calls, such as `echo "$TOKEN" | docker login --password-stdin`, are skipped, also inside a command substitution (`V=$(echo "$X" | cut -c2-)`).

This is especially dangerous in security-sensitive contexts:
- A failed `curl | bash` download still "succeeds" — bash executes with empty input and exits 0
- A failed secret-fetching step before a deployment is ignored
- Corrupted data passes through to downstream steps undetected

Analogous to ansible-lint's `risky-shell-pipe` rule.

## Trigger example

```yaml
build:
  script:
    - curl https://install.example.com/tool.sh | bash   # if curl fails, bash runs on empty input
    - generate-config | tee config.yml                  # if generate-config fails, job still passes
```

## Safe alternatives

**Set once at the top of the script:**
```yaml
build:
  script:
    - set -o pipefail
    - generate-config | tee config.yml
    - curl https://install.example.com/tool.sh | bash
```

**Set as part of a combined shell options header:**
```yaml
build:
  script:
    - set -euo pipefail
    - generate-config | tee config.yml
```

**Set inline per line:**
```yaml
build:
  script:
    - set -o pipefail && generate-config | tee config.yml
```

**Set in `before_script` to apply to all jobs using the same template:**
```yaml
.base:
  before_script:
    - set -o pipefail

build:
  extends: .base
  script:
    - generate-config | tee config.yml
```

## Notes

- One finding is emitted per job, pointing to the first pipeline that needs `pipefail` (inside a `|` block, the line itself). When more than one line needs `pipefail`, the message includes the count, for example `(3 piped lines in this job, first shown)`; a single affected line keeps the original message. Each pipeline is counted at its starting line, so multiple pipes or pipelines starting on the same line count once, including backslash-continued pipelines. Skipped `echo`/`printf` pipelines do not contribute to the count.
- `||` (logical OR), `>|` (forced redirect) and the `|` between `case` patterns (`main | release-*)`) are not pipes. `|&` pipes stdout and stderr, so it counts.
- A `|` inside quotes is part of an argument, as in `sed "s|a|b|"` or `grep "a|b"`, and does not count. A command substitution inside double quotes is a command of its own, so the pipe in `X="$(a | b)"` counts. Here-document bodies are data and are not read.
- `pipefail` set anywhere in `before_script`, `script`, `after_script`, or a `run:` step suppresses the finding. So does a `before_script` or `script` the job inherits through `extends:` from a job in the same file, from `default:`, or from a top-level `before_script:`, unless the job defines that section itself or opts out with `inherit: default:`.
- Jobs whose runner tags select a Windows runner (a tag containing the word `windows`, such as `windows`, `saas-windows-medium-amd64` or `windows-v2:2022`, also through `extends:` or `default: tags`) are skipped: their scripts run in PowerShell, which has no `pipefail`.
- If you intentionally ignore a pipe failure (e.g. `cmd | true`), suppress the finding inline: `# glsec:ignore GL024 -- intentional, fallback handled`.
