# GL024 — Pipe in a new shell without `pipefail`

**Severity:** `info`  
**OWASP:** [CICD-SEC-7 – Insecure System Configuration](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-07-Insecure-System-Configuration)

## What glsec checks

A pipeline's exit code is the exit code of its **last** command unless `pipefail` is set; an earlier command can fail and the pipeline still succeeds.

GitLab Runner's bash and sh shells start every job script with `set -o pipefail` when the shell supports it (bash, BusyBox ash in Alpine, current dash):

```sh
case "$(set -o)" in *"pipefail"*) set -o pipefail;; esac; set -o errexit
```

So a pipe in `before_script:`, `script:` or `after_script:` already fails the job when an earlier command fails, and glsec does not report it.

glsec reports a pipe in a script that a **new shell** runs, which starts without the option, also when the job sets `pipefail`:

- the argument of `sh -c`, `bash -c` and the other POSIX shells, also with bundled flags (`sh -ec`) and inside a wrapper (`docker run img sh -c …`, `kubectl exec pod -- sh -c …`, `sudo bash -c …`)
- the remote command of `ssh host '…'`

A pipe there counts only when its status matters: under errexit (`sh -ec`, `set -e` or `set -o errexit` in the script), as the script's last command, or before `&&`. Without errexit, the shell ignores a failed command in the middle of the script anyway.

## Trigger example

```yaml
build:
  script:
    - docker run --rm alpine:3.20 sh -c "generate-config | tee config.yml"   # if generate-config fails, the job still passes
    - ssh deploy@host "journalctl -u app | tail"
```

## Safe alternatives

**Set it in the script the new shell runs:**

```yaml
build:
  script:
    - docker run --rm alpine:3.20 sh -c "set -o pipefail; generate-config | tee config.yml"
```

**Or on the shell's command line:**

```yaml
build:
  script:
    - bash -o pipefail -c "generate-config | tee config.yml"
```

## Notes

- One finding is emitted per job, pointing to the first command that starts such a shell (inside a `|` block, the line itself). When more than one command does, the message includes the count, for example `(3 piped lines in this job, first shown)`.
- Not reported: pipelines whose commands before the last only print (`echo "$TOKEN" | docker login --password-stdin`), pipelines tested as a condition (`if`/`while`/`until … | grep -q x`, a final `grep -q` or `grep … >/dev/null`), pipelines followed by `||`, and pipelines inside a command substitution (`$(a | b)`), whose status is lost.
- `||` (logical OR), `>|` (forced redirect) and the `|` between `case` patterns (`main | release-*)`) are not pipes. A `|` inside quotes in the new shell's script is part of an argument, as in `sed "s|a|b|"`.
- `set +o pipefail` in the job turns the option off on purpose (`yes | sdkmanager --licenses`) and is not reported.
- Jobs whose runner tags select a Windows runner (a tag containing the word `windows`, such as `windows`, `saas-windows-medium-amd64` or `windows-v2:2022`, also through `extends:` or `default: tags`) are skipped: their scripts run in PowerShell, which has no `pipefail`.
- Before 1.26.0, GL024 reported every pipe in a job without `set -o pipefail` as `warn`. Entries for those findings in a `.glsec-ignore` file or a baseline no longer match anything.
- To suppress a finding inline: `# glsec:ignore GL024 -- intentional, fallback handled`.
