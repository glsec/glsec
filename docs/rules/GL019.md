# GL019 — Deploy job missing `resource_group:`

**Severity:** `warn`  
**OWASP:** [CICD-SEC-1 – Insufficient Flow Control Mechanisms](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-01-Insufficient-Flow-Control-Mechanisms)

## What glsec checks

glsec flags deployment and publish jobs that do not have a `resource_group:` key. Without it, multiple pipeline runs can execute the same deploy job concurrently — causing race conditions, partial deploys, overwritten state, or conflicting releases.

A job is considered a deployment/publish job if it has:
- An `environment:` key, unless its `action:` is `prepare`, `verify` or `access` (those only use the environment) or its tier is `development` or `testing`: its `deployment_tier:` or, without one, the tier GitLab guesses from the environment name (`review/…`, `dev`, `test`, `qa`, …) (review apps and previews, where a cancelled or overlapping run does no harm), or
- A `stage:` value containing `deploy`, `release`, `publish`, or `ship`

A stage whose words say it tests or checks (`test`, `lint`, `check`, `coverage`, `validate`, `audit`, `scan`, `note`, `changelog`, `cleanup`, matched at the start of a word, so `deployment test` but not `latest`) is not a deploy stage. Nor is one that builds (`build`, `compile`, `assemble`) unless it also names a strong deploy word (`deploy`, `publish`, `push`, `upload`, `rollout`, `ship`): `release-build` builds, `build-and-publish` publishes.

`resource_group:`, `environment:` and `stage:` count when the job inherits them through `extends:` (from a job in the same file). Hidden jobs (names starting with `.`) are not reported; the jobs extending them are. A job extending a template from another file is skipped. In a file with `include:`, a job without `script:`, `trigger:` or `run:` (its own or from a same-file template) is skipped too: GitLab merges it into the included job of the same name, which may carry the missing key.

## Trigger example

```yaml
deploy-prod:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  # no resource_group: — two pipeline runs can deploy simultaneously
```

## Safe alternative

```yaml
deploy-prod:
  stage: deploy
  environment: production
  resource_group: production
  script:
    - ./deploy.sh
```

GitLab serialises jobs in the same `resource_group` — the second run waits until the first completes. Use separate group names per environment (e.g. `staging`, `production`) if you want concurrent deploys across environments but serialised deploys within each.

## Why this matters

Without concurrency control, two developers merging to the same branch within seconds of each other can trigger overlapping deploys. The later deploy may start before the earlier one finishes, causing:
- Configuration to be applied out of order
- Database migrations to run twice or in the wrong sequence
- Health checks to pass against the wrong version
- Partial state visible to end users
