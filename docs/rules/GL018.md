# GL018 — Secret variable re-exported at pipeline level

**Severity:** `warn`  
**OWASP:** [CICD-SEC-6 – Insufficient Credential Hygiene](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene)

## What glsec checks

glsec flags pipeline-level `variables:` entries (top-level, `default:`, or in a `workflow:rules` entry, which applies to every job) whose name ends with a secret-indicating suffix (`_TOKEN`, `_SECRET`, `_PASSWORD`, `_PASSWD`, `_PASS`, `_PWD`, `_KEY`, `_CREDENTIAL`, `_CERT`) and whose value is exactly one CI variable reference (`$VAR` or `${VAR}`). A composite value such as `"${CI_PROJECT_NAMESPACE}:${CI_PROJECT_NAME}"` is not a re-exported secret. Neither is a predefined variable, which every job gets anyway: a predefined credential (`$CI_JOB_TOKEN`, `$CI_REGISTRY_PASSWORD`, `$CI_DEPENDENCY_PROXY_PASSWORD`, `$CI_DEPLOY_PASSWORD`) or a `CI_`/`GITLAB_` name that doesn't look secret (`$CI_COMMIT_REF_SLUG`). A secret-looking `CI_` name such as `$CI_API_TOKEN` is a project setting and is still reported. A variable that references itself (`X: $X`) is not reported: it widens nothing, since the value is already visible under the same name wherever it is set.

This pattern re-exports a GitLab Settings variable at the pipeline level, making it available to **every job** in the pipeline — including test jobs, lint jobs, and jobs triggered by merge requests from untrusted forks. If any of those jobs are compromised (e.g. via a poisoned dependency or injected script), the secret is accessible.

## Trigger example

```yaml
variables:
  PROD_DB_PASSWORD: $PROD_DB_PASSWORD   # available to all jobs
  AWS_SECRET_ACCESS_KEY: $PROD_AWS_KEY

test:
  script: npm test  # gets PROD_DB_PASSWORD and AWS_SECRET_ACCESS_KEY for free

deploy:
  environment: production
  script: ./deploy.sh  # the only job that actually needs these
```

## Safe alternatives

**Move the variable to job level** so only the job that needs it has access:

```yaml
deploy:
  environment: production
  variables:
    PROD_DB_PASSWORD: $PROD_DB_PASSWORD   # only available in this job
  script: ./deploy.sh
```

**Use GitLab Settings environment scoping** (Settings → CI/CD → Variables → Environment scope): restrict the variable to the `production` environment so it is only injected into jobs with `environment: production`.

## Notes

- Only pipeline-level `variables:` entries are flagged — job-level variables, including those of a job's `rules:` entries, are appropriately scoped and not reported.
- A variable referencing itself (`X: $X`) is not flagged.
- Literal values (non-variable-reference) with secret-indicating names are covered by GL006, not this rule.
- Both scalar and extended forms are checked:

  ```yaml
  variables:
    DEPLOY_TOKEN:
      value: $DEPLOY_TOKEN
      description: "Used by deploy job"
  ```
