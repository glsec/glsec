# GL080 — Sensitive job with no pipeline-source guard

**Severity:** `warn`  
**OWASP:** [CICD-SEC-1 – Insufficient Flow Control Mechanisms](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-01-Insufficient-Flow-Control-Mechanisms)  

## Risk

A privileged job with **no pipeline-source guard at all** runs on every pipeline source — including **fork merge requests**, where an external contributor controls the code. Without a `rules:if` that inspects `$CI_PIPELINE_SOURCE` (or an equivalent restriction), a deploy/publish/release job is an absent flow-control gate: untrusted contributors can trigger it.

## What glsec checks

GL080 flags a job when **all** of the following hold:

1. **The job is sensitive** — it has a real deploy signal, not merely a deploy-sounding name. A deploy-named job that only builds a local artifact, runs tests, or writes files has no credential to steal on a fork MR, so a name alone is not enough (#1371). A job is sensitive when:
   - it declares a named `environment:` (other than an `action: stop` teardown), or it is a GitLab Pages job (the main-site case is [GL013](GL013.md)'s); or
   - its **effective script runs a real deploy, publish or infrastructure-apply command** — `docker`/`podman push`, `npm`/`cargo`/`twine`/`gem` publish, `kubectl apply`/`rollout`, `helm upgrade`/`install`, `terraform`/`tofu apply`, `pulumi up`, `rsync`/`scp`, … This catches an infra-apply job whose name is `terraform` or `plan-apply`, not `deploy`. A local build such as `dotnet publish -o out` is not a deploy; only `dotnet nuget push` is; or
   - its name or stage matches a narrow deploy keyword (`deploy`, `rollout`, `release`, `publish`, `provision`) **and** it uses a credential (a secret-named variable, in `variables:` or referenced as `$DEPLOY_TOKEN` in the script), so a custom deploy glsec can't read as a command (`./deploy.sh "$TOKEN"`) still counts. Build/test/package keywords (`build`, `test`, `dist`, …) veto the name match.
2. **The job has no effective guard** — either no `rules:` / `only:` / `except:` at all, **or** a `rules:` block whose items carry no `if:` / `changes:` / `exists:` condition (e.g. only `when: always` / `when: on_success`), so the gate imposes no restriction.
3. **No restricting `workflow:rules`** — the top-level `workflow:rules` does not carry an `if:` condition that would already gate which pipeline sources run.

A `when: manual` gate — whether top-level or inside a `rules:` item — is **not** a pipeline-source restriction, so it does not satisfy point 2: the job is still created on every source, and a maintainer can start it on a fork merge request, where it runs the fork's code with the job's credentials. GL080 still flags such a job, but words the finding for the manual case (a maintainer click, not an external trigger) rather than the generic no-guard case.

To avoid false positives on guards glsec cannot resolve, GL080 **skips**:

- **Hidden jobs** (names starting with `.`) — templates GitLab never runs.
- **Jobs that extend a template from another file** (an `include:`) — the guard may be there. A template in the same file is merged in the way GitLab merges it, and so are YAML merge keys (`<<:`), so a guard from either is seen like one written inline. In a file with `include:`, a job without `script:`, `trigger:` or `run:` (its own or from a same-file template) is skipped too: GitLab merges it into the included job of the same name, which may carry the missing key.
- **Rules taken from a `!reference`** count as a guard: what they stand for can't be read here.

### Deploys and publishes that run only in merge request pipelines

A guard can also point the wrong way. A sensitive job whose rules let it run **only in merge request pipelines** has an effective guard, but it deploys or publishes the MR's source commit before anyone merged it. To work there, its credentials can't be protected variables: a pipeline for an unprotected source branch doesn't get them. So every developer who can push a branch can read them. GL080 reports such a job (#1142) when:

- every rule that lets it run requires a merge request pipeline: `$CI_PIPELINE_SOURCE == "merge_request_event"`, a positive test of a `$CI_MERGE_REQUEST_*` variable, or `only: [merge_requests]`. `when: never` rules are skipped; an `&&` with a `$CI_COMMIT_BRANCH`/`$CI_COMMIT_TAG` operand, or a second rule that admits a branch, makes it no MR-only job;
- it has no `environment:` (GL013 reports a production one, and any other is a review app);
- it has a production signal:
  - `prod`, `production` or `live` as a word of the job or stage name (`deploy_prod`, `go-live`), not `preprod`/`pre-prod`/`non-prod`; or
  - a package publish command (`npm`/`pnpm`/`yarn publish`, `twine upload`, `poetry`/`uv`/`flit`/`hatch`/`pdm publish`, `gem push`, `rake release`). A dry run, or a publish to TestPyPI or the project's own GitLab package registry (`$CI_API_V4_URL`, `$CI_JOB_TOKEN`, also in the job's `variables:`), is not counted.

This also applies with a `workflow:rules` that admits merge request pipelines; one that keeps them out (`if: $CI_COMMIT_BRANCH` only) silences it.

```yaml
deploy_prod:
  stage: deploy
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"
  script:
    - scp build.tgz deploy@prod.example.invalid:.
```

Restrict such a job to the protected branch (`$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH`) or to tags, and make its credentials protected variables.

## Trigger example

```yaml
deploy-prod:
  stage: deploy
  script:
    - ./deploy.sh          # no rules: — runs on fork MR pipelines too

publish:
  stage: deploy
  rules:
    - when: on_success     # no if: — imposes no source restriction
  script:
    - ./publish.sh
```

## Safe alternative

Gate the job on the pipeline source (and, for deploys, restrict to the intended branches):

```yaml
deploy-prod:
  stage: deploy
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == "main"'
  script:
    - ./deploy.sh
```

A restricting top-level `workflow:rules` gates every job, in which case GL080 does not fire.

## Relationship to other rules

- **GL013** flags a production-environment deploy job or a job publishing the main GitLab Pages site with no `rules:`/`only:`, and a production-environment deploy that runs only in merge request pipelines. GL080 **defers** to GL013 for those cases and covers the gaps: jobs sensitive by *stage/name* (not `environment:`), jobs whose `rules:` block exists but imposes no condition, and MR-only production deploys and publishes without `environment:`.
- **GL074** flags a tautological (always-true) `rules:if`. GL080 covers the *missing/ineffective* gate — no `if:` at all — rather than an always-true one.
- **GL053** flags a missing or unrestricted top-level `workflow:rules` at the pipeline level.

## False-positive note

Not every deploy-stage job without `rules:` is exploitable — many legitimately rely on a restricting `workflow:rules` (which GL080 already accounts for) or on branch-scoped runners. Review each finding in context.
