# GL080 — Sensitive job with no pipeline-source guard

**Severity:** `warn`  
**OWASP:** [CICD-SEC-1 – Insufficient Flow Control Mechanisms](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-01-Insufficient-Flow-Control-Mechanisms)  

## Risk

A privileged job with **no pipeline-source guard at all** runs on every pipeline source — including **fork merge requests**, where an external contributor controls the code. Without a `rules:if` that inspects `$CI_PIPELINE_SOURCE` (or an equivalent restriction), a deploy/publish/release job is an absent flow-control gate: untrusted contributors can trigger it.

## What glsec checks

GL080 flags a job when **all** of the following hold:

1. **The job is sensitive** — it has a real deploy signal, not merely a deploy-sounding name. A deploy-named job that only builds a local artifact, runs tests, or writes files has no credential to steal on a fork MR, so a name alone is not enough (#1371). A job is sensitive when:
   - it declares a named `environment:` (other than an `action: stop` teardown), or it is a GitLab Pages job (the main-site case is [GL013](GL013.md)'s). Two kinds of environment don't count on their own (#1497), because each branch gets its own and it holds nothing another branch depends on:
     - one whose tier is `development` or `testing`. The tier comes from `deployment_tier:`, or else from the name, as GitLab guesses it: `dev`, `review/…`, `test`, `qa`, `int`, and so on;
     - one whose name is made per branch, commit, pipeline or merge request, with the variables listed below (`review/$CI_COMMIT_REF_SLUG`, `mr-$CI_MERGE_REQUEST_IID`).

     The name is expanded through the job's and the file's `variables:` and, for a `rules:` entry that is reported, that entry's `variables:` (`- variables: {ENV_NAME: review/$CI_COMMIT_REF_SLUG}`). Such a job still counts through its script or a deploy name with a credential. A per-run name that GitLab guesses as production (`prod/$CI_COMMIT_REF_SLUG`), or an explicit `deployment_tier: production`, still counts; or
   - its **effective script runs a real deploy, publish or infrastructure-apply command** — `docker`/`podman push`, `npm`/`cargo`/`twine`/`gem` publish, `kubectl apply`/`rollout`, `helm upgrade`/`install`, `terraform`/`tofu apply`, `pulumi up`, `rsync`/`scp`, … This catches an infra-apply job whose name is `terraform` or `plan-apply`, not `deploy`. A local build such as `dotnet publish -o out` is not a deploy; only `dotnet nuget push` is. Nor is a command that ships nothing another branch depends on (#1492): a `docker`/`podman`/`buildah`/`nerdctl push` of one image whose tag is made from the branch, commit, pipeline, job or merge request (`$CI_COMMIT_REF_SLUG`, `$CI_COMMIT_REF_NAME`, `$CI_COMMIT_BRANCH`, `$CI_COMMIT_SHA`, `$CI_COMMIT_SHORT_SHA`, `$CI_PIPELINE_ID`, `$CI_PIPELINE_IID`, `$CI_JOB_ID`, `$CI_MERGE_REQUEST_IID`), also when the image goes through variables set in the job's or the file's `variables:` (`"$IMG-debug"` with `IMG: $CI_REGISTRY_IMAGE:$CI_PIPELINE_ID`), or a dry run (`--dry-run`, `--dry-run=client`, `dart pub publish -n`). Also not a deploy: a command that only prints its usage (`--help`, or `-h` or `help` as the last word), `pixi publish` without `--to`/`--target-channel` (it copies the package into a local directory), `kubectl` and `helm` in a job that starts its own throwaway cluster (`kind create cluster`, `k3d cluster create`, `minikube start`), `rsync`/`scp` as part of another word (`scp-runner`, `librsync`, `./cmd/scp-wallet`) or with no remote operand (`rsync -a ~/.cache home/`), and a publish to a `services:` container of the same job, when every URL the script uses is on such a service or `localhost`. A per-run variable in the image's repository (`$CI_REGISTRY_IMAGE/build-$CI_COMMIT_REF_SLUG`) counts like one in the tag, and the image is also followed through shell assignments earlier in the script (`if [ -n "$CI_COMMIT_TAG" ]; then T=…; else T=$BRANCH_IMAGE; fi`).

     A step guarded in the script counts as guarded, as a `rules:` guard would: a command in an `if` whose test is true only on a protected or named ref (`[ "$CI_COMMIT_BRANCH" = "main" ]`, `[[ $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH ]]`, `[ "$CI_COMMIT_REF_PROTECTED" = true ]`, `[ -n "$CI_COMMIT_TAG" ]`; not `$CI_COMMIT_REF_NAME`, which in a merge request pipeline holds the source branch's name, and not an unquoted operand of `[` that can vanish when empty), the `else` branch of the negated test, a command after such a test and `&&`, and every script line after an early exit off those refs (`if [ "$CI_COMMIT_BRANCH" != main ]; then exit 0; fi`, `[ -n "$CI_COMMIT_TAG" ] || exit 0`). `after_script` runs in a shell of its own, so an exit in the script doesn't guard it. A compound test, a pattern (`release*`), an `elif` or a nested `if`, or a test on another variable is not read and leaves the step counted, and an exit guard counts only as a command of the script itself, not in a comment, a string, a subshell, a function, a loop or another `if`. A variable the script assigns more than once counts as per run only when every value is. A push of `latest`, of an image without a tag, of a fixed tag or a version (`$CI_COMMIT_TAG`), or with `--all-tags` still counts: any branch can overwrite what others pull; or
   - its name or stage matches a narrow deploy keyword (`deploy`, `rollout`, `release`, `publish`, `provision`) **and** it uses a credential (a secret-named variable, in `variables:` or referenced as `$DEPLOY_TOKEN` in the script), so a custom deploy glsec can't read as a command (`./deploy.sh "$TOKEN"`) still counts. Build/test/package keywords (`build`, `test`, `dist`, …) veto the name match.
2. **The job has no effective guard** — one of these holds, so the gate imposes no restriction:
   - no `rules:` / `only:` / `except:` at all;
   - a `rules:` block whose items carry no `if:` / `changes:` / `exists:` condition (only `when: always` / `when: on_success`);
   - **a `rules:` entry without `if:` (#1498)**: a `when:` fallback such as `- when: manual` after a default-branch rule, or `changes:`/`exists:` alone, which is also true for every new branch. GitLab runs the job by the first entry that matches, so such an entry lets every branch run it. An earlier `when: never` entry stops the check: glsec reports the fallback only when nothing before it can keep a ref out. An `if:` that only tests that a branch is set, or one that admits merge request pipelines, is not counted here.
3. **No `workflow:rules` that admits protected refs only** — every entry that lets a pipeline run restricts to the default branch, a named branch, a tag or `$CI_COMMIT_REF_PROTECTED == "true"`, and none admits merge request pipelines. Any other workflow still runs the job on every branch: one that admits every push (`$CI_PIPELINE_SOURCE == "push"`), every branch (`$CI_COMMIT_BRANCH`), or GitLab's recommended switch between branch and merge request pipelines (#1492). A workflow entry glsec can't read, such as a `!reference` into an included file, counts as admitting anything.

A `when: manual` gate — whether top-level or inside a `rules:` item — is **not** a pipeline-source restriction, so it does not satisfy point 2: the job is still created on every source, and a maintainer can start it on a fork merge request, where it runs the fork's code with the job's credentials. GL080 still flags such a job, but words the finding for the manual case (a maintainer click, not an external trigger) rather than the generic no-guard case.

To avoid false positives on guards glsec cannot resolve, GL080 **skips**:

- **Child pipelines and conditionally included files that only protected refs reach** (#1502): every trigger job that starts the child, or every `include:` entry with `rules:` that pulls the file in, runs on protected refs only. In a child started on any ref, `if: $CI_PIPELINE_SOURCE == "parent_pipeline"` restricts nothing. A production deploy whose open `rules:` entry GL013 reports isn't reported again.
- **Hidden jobs** (names starting with `.`) — templates GitLab never runs.
- **Jobs that extend an unresolvable cross-file template** (such as a remote `include:` or a scan without include resolution) — the guard may be there. A template in the same file or from a resolved local `include:` is merged in the way GitLab merges it, and so are YAML merge keys (`<<:`), so a guard from either is seen like one written inline. In a file with `include:`, a job without `script:`, `trigger:` or `run:` (its own or from a same-file or resolved local-include template) is skipped too: GitLab merges it into the included job of the same name, which may carry the missing key.
- **Rules taken from a `!reference`** count as a guard: what they stand for can't be read here.

### Deploys and publishes that run only in merge request pipelines

A guard can also point the wrong way. A sensitive job whose rules let it run **only in merge request pipelines** has an effective guard, but it deploys or publishes the MR's source commit before anyone merged it. To work there, its credentials can't be protected variables: a pipeline for an unprotected source branch doesn't get them. So every developer who can push a branch can read them. GL080 reports such a job (#1142) when:

- every rule that lets it run requires a merge request pipeline: `$CI_PIPELINE_SOURCE == "merge_request_event"`, a positive test of a `$CI_MERGE_REQUEST_*` variable, or `only: [merge_requests]`. `when: never` rules are skipped; an `&&` with a `$CI_COMMIT_BRANCH`/`$CI_COMMIT_TAG` operand, or a second rule that admits a branch, makes it no MR-only job;
- it has no `environment:` (GL013 reports a production one, and any other is a review app);
- it has a production signal:
  - `prod`, `production` or `live` as a word of the job or stage name (`deploy_prod`, `go-live`), not `preprod`/`pre-prod`/`non-prod`; or
  - a package publish command (`npm`/`pnpm`/`yarn publish`, `twine upload`, `poetry`/`uv`/`flit`/`hatch`/`pdm publish`, `gem push`, `rake release`). A dry run, or a publish to TestPyPI or the project's own GitLab package registry (`$CI_API_V4_URL`, `$CI_JOB_TOKEN`, also in the job's `variables:`), is not counted.

This also applies with a `workflow:rules` that admits merge request pipelines; one that keeps them out (`if: $CI_COMMIT_BRANCH` only) silences it.

```yaml
deploy_prod:
  stage: deploy
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"
  script:
    - scp build.tgz deploy@prod.example.invalid:.
```

Restrict such a job to the protected branch (`$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH`) or to tags, and make its credentials protected variables.

## Trigger example

```yaml
deploy-prod:
  stage: deploy
  script:
    - ./deploy.sh          # no rules: — runs on fork MR pipelines too

publish:
  stage: deploy
  rules:
    - when: on_success     # no if: — imposes no source restriction
  script:
    - ./publish.sh
```

## Safe alternative

Gate the job on the pipeline source (and, for deploys, restrict to the intended branches):

```yaml
deploy-prod:
  stage: deploy
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == "main"'
  script:
    - ./deploy.sh
```

A top-level `workflow:rules` that admits protected refs only gates every job, in which case GL080 does not fire.

## Relationship to other rules

- **GL013** flags a production-environment deploy job or a job publishing the main GitLab Pages site with no `rules:`/`only:`, and a production-environment deploy that runs only in merge request pipelines. GL080 **defers** to GL013 for those cases and covers the gaps: jobs sensitive by *stage/name* (not `environment:`), jobs whose `rules:` block exists but imposes no condition, and MR-only production deploys and publishes without `environment:`.
- **GL074** flags a tautological (always-true) `rules:if`. GL080 covers the *missing/ineffective* gate — no `if:` at all — rather than an always-true one.
- **GL053** flags a missing or unrestricted top-level `workflow:rules` at the pipeline level.

## False-positive note

Not every deploy-stage job without `rules:` is exploitable — many legitimately rely on a `workflow:rules` restricted to protected refs (which GL080 already accounts for) or on branch-scoped runners. Review each finding in context.
